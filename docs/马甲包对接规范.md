# 马甲包对接规范

面向：马甲包 iOS / Android 研发
Web 侧：`web1` 分支，版本 `1.0.2`
日期：2026-11-08

---

## 分工

App = 原生壳 + WebView 加载 IM Web。业务逻辑、UI、长连接、消息收发全在 Web 内。原生壳负责五件事：

1. 注入 `window.__SSG_SHELL__`，让 Web 知道自己在壳里（§1）
2. 转述系统状态：前后台、网络、内存（§4）
3. 推送：集成 OneSignal，处理通知点击（§5）
4. 提供干净稳定的 WebView 运行环境（§6～§9），冷启动直接进 Web（§9.6）
5. 在 Web 失去自救能力时把它捅醒（§10、§11）

本规范的接口 Web 侧均已实现，原生实现即生效。接口和行为以本规范为准，Web 侧不会为单个马甲包单独改动。

### 优先级

P0：容器注入（§1）、URL `channelCode` 与 UA 追加（§2）、事件接收通道（§3）、生命周期回调（§4）、OneSignal 绑定与深链（§5）、权限声明与申请时机（§6）、文件选择器与麦克风授权与渲染进程恢复（§7）、HTTPS 与内核版本与存储持久与 Android 承载方式（§8）、返回键与键盘与启动无多余加载（§9.1、§9.2、§9.6）、回前台信号与不冻结定时器与单实例（§10）、原生心跳与存活监测（§11.1、§11.2）、应用名称（§13.1）

P1：前台抑制与角标（§5.4）、全屏视频与外链与 `window.open`（§7）、`textZoom` 与安全区（§9）、推送捅醒与内存告警与诊断字段与日志导出（§11.3～§11.6）

P2：内核过低引导升级（§11.7）

# 1. 容器注入

注入是其余所有功能的前置。没有它，Web 按「普通浏览器」口径运行。

## 1.1 对象

```js
window.__SSG_SHELL__ = {
  platform: 'android',               // 必填，只接受 'android' / 'ios'
  bundleId: 'com.example.app',       // 必填，推送路由依赖
  shellVersion: '1.2.3',             // 必填
  webviewVersion: '120.0.6099.230',  // 必填
  deviceModel: 'Xiaomi 14',          // 必填，见 §11.5
  osVersion: '14',                   // 必填，见 §11.5
};
```

`platform` 缺失或为空视为注入无效。`bundleId` 缺失则 Web 不上报包名，该设备收不到推送。版本与机型字段只进诊断埋点。

## 1.2 注入时机

必须在页面任何脚本执行之前完成。Web 侧有一组常量在模块加载那一刻求值（容器判定、重连参数、装机卡片开关），晚于首个 bundle 即无效。

iOS：

```swift
let js = """
window.__SSG_SHELL__={platform:'ios',bundleId:'\(Bundle.main.bundleIdentifier ?? "")',\
shellVersion:'\(shellVer)',webviewVersion:'\(webkitVer)',\
deviceModel:'\(deviceModel)',osVersion:'\(osVer)'};
"""
config.userContentController.addUserScript(
    WKUserScript(source: js,
                 injectionTime: .atDocumentStart,
                 forMainFrameOnly: true))
```

Android（依赖 androidx.webkit）：

```kotlin
WebViewCompat.addDocumentStartJavaScript(
    webView,
    "window.__SSG_SHELL__={platform:'android',bundleId:'${ctx.packageName}'," +
        "shellVersion:'$shellVer'," +
        "webviewVersion:'${WebViewCompat.getCurrentWebViewPackage(ctx)?.versionName}'," +
        "deviceModel:'${Build.MODEL}',osVersion:'${Build.VERSION.RELEASE}'};",
    setOf("*")
)
```

必须用 `addDocumentStartJavaScript`。`onPageStarted` 里 `evaluateJavascript` 与首个 bundle 存在竞态，不接受。

## 1.3 自检

界面上看：App 内看不到「下载客户端」卡片。卡片还在就是注入没生效，不用连调试器。

调试器里看（`chrome://inspect` / Safari 开发菜单）：

```js
document.documentElement.classList.contains('is-web-browser')   // 必须 false
```

这是 Web 侧的判定结果。只要它是 `true`，无论 `window.__SSG_SHELL__` 打印出什么都算失败，通常是时机晚了。

## 1.4 兜底

Web 对 Android 的 `window.jsBridge`、iOS 的 `webkit.messageHandlers` 做了存在性兜底识别，诊断字段标记为 `shellSrc:bridge`。它只保证容器判定，拿不到 `bundleId` 和版本号，不能替代注入。交付标准是 `shellSrc:inject`。

# 2. URL 与 UA

## 2.1 channelCode

渠道码通过 H5 落地链接的查询参数传入，**可选**。各渠道打包时把渠道码写进要加载的落地 URL：

```
https://<域名>/?channelcode=<渠道码>
```

**壳要做的只有一件事：把配置好的落地 URL 原样加载，不要改。**

```kotlin
webView.loadUrl(落地URL)   // 落地URL 里带什么就加载什么，不解析、不重拼 query
```

- 链接带渠道码就原样透传给 Web，不带就不加。**壳不得 strip 掉链接里的渠道码参数，不得用占位符或编译期常量覆盖它。**
- 大小写、取值、落库全由 Web 负责，壳不用管：Web 在 `src/util/nativeBridge.ts` 里大小写不敏感地取 `channelcode`（`channelcode` / `ChannelCode` / 任意大小写都认），存入 sessionStorage，后续 `eventRegister` / `eventLogin` / `eventMessageSent` 自动带上。
- URL 不带渠道码是允许的：渠道归因此时不可用，但不算接入缺陷。

> 两个常见坏法（都会让 Web 取不到真实渠道码）：① `query.removeWhere((k,_) => k.toLowerCase() == 'channelcode')` 把链接里的渠道码删了；② 用 dart-define / 编译期常量把渠道码硬覆盖成固定值（如 `ChannelCode_google`），无视链接实际传入的值。

## 2.2 UA

```
<原始 UA> SSGShell/<shellVersion> <Android|iOS>
```

- iOS：`config.applicationNameForUserAgent = "SSGShell/\(ver) iOS"`
- Android：`webView.settings.userAgentString += " SSGShell/$ver Android"`

必须追加，不能整段替换。Web 与服务端都有按 UA 判平台的逻辑（`Android`、`iPhone`、`iPad`），替换会让平台识别全面失效。

# 3. Web → Native 事件

## 3.1 事件表

| handler 名 | eventName | params | 触发时机 |
|---|---|---|---|
| `eventWebReady` | `webReady` | `timestamp` | 首屏（会话列表或登录页）已可见、可接受 `openChat`。每次页面加载发一次，最晚在初始化后 8 秒发出。不保证早于 `login` |
| `eventRegister` | `register` | `channelCode`, `uid`, `timestamp` | 注册成功，同一设备只发一次 |
| `eventLogin` | `login` | `channelCode`, `uid`, `timestamp` | 登录或恢复登录，同一 uid 只发一次 |
| `eventLogout` | `logout` | `uid`, `timestamp` | 退出登录或被踢下线 |
| `eventMessageSent` | `messageSent` | `channelCode`, `uid`, `timestamp` | 消息发送成功（服务端确认后），每条消息一次 |
| `eventWebAlive` | `webAlive` | `timestamp` | 前台每 15 秒一次，见 §11.2 |
| `eventChatOpen` | `chatOpen` | `chatId`, `timestamp` | 进入某个会话，见 §5.4 |
| `eventChatClose` | `chatClose` | `chatId`, `timestamp` | 离开会话：回到会话列表、切到其他会话、退出登录 |
| `eventChatRead` | `chatRead` | `chatId`, `timestamp` | 当前会话已读完（未读数归零），见 §5.4 |
| `eventUnreadCount` | `unreadCount` | `count`, `timestamp` | 未读总数变化时（不含免打扰会话），见 §5.4 |

params 字段全部是字符串：

```json
{
  "eventName": "login",
  "params": { "channelCode": "ch001", "uid": "1571277787", "timestamp": "1762000000000" }
}
```

## 3.2 iOS 接收

§3.1 的十个 handler 全部注册，未注册的会抛异常，Web 已捕获但事件会丢。

```swift
["eventWebReady", "eventRegister", "eventLogin", "eventLogout",
 "eventMessageSent", "eventWebAlive",
 "eventChatOpen", "eventChatClose", "eventChatRead", "eventUnreadCount"].forEach {
    config.userContentController.add(self, name: $0)
}
```

Web 调 `window.webkit.messageHandlers.<handler>.postMessage(payload)`，payload 是 JS 对象（原生侧为 `NSDictionary`），不是 JSON 字符串。

## 3.3 Android 接收

对象名必须是 `jsBridge`，方法名 `postMessage`。Web 优先调两参版本，抛异常时退化为单参版本，所以两参必须实现，单参可选。

```kotlin
class JsBridge {
    @JavascriptInterface
    fun postMessage(name: String, json: String) { }

    @JavascriptInterface
    fun postMessage(json: String) { }
}
webView.addJavascriptInterface(JsBridge(), "jsBridge")
```

# 4. Native → Web 回调

Web 启动时在页面上挂出 `window.__ssgShell`：

| 方法 | 入参 | 调用约定 |
|---|---|---|
| `onForeground()` | 无 | 每次回前台立即调，见 §10.2 |
| `onBackground()` | 无 | 进后台时调 |
| `onNetwork(type)` | `wifi` / `cellular` / `ethernet` / `other` | 网络真正可用后调，去抖 1～2 秒；其他取值归为 `other`。断网时不用调，传 `none` 会被忽略。见 §10.4 |
| `onHeartbeat()` | 无 | 前台每 20 秒，见 §11.1 |
| `onMemoryWarning()` | 无 | 系统内存告警时，见 §11.4 |
| `openChat(payload)` | `{ chatId, messageId? }` 或其 JSON 字符串 | 见 §5.3 |

`window.__ssgShell` 由 Web 在启动流程中创建，页面加载早期不存在，每次重新加载会重建。调用前判空，不存在时跳过，不要重试轰炸：

```kotlin
webView.evaluateJavascript("window.__ssgShell && window.__ssgShell.onForeground()", null)
```

```swift
webView.evaluateJavaScript("window.__ssgShell && window.__ssgShell.onForeground()")
```

# 5. 推送（OneSignal）

## 5.1 链路

```
登录 → 原生把设备绑到 uid → 对端发消息 → 服务端按 uid 调 OneSignal
     → APNs / FCM → 手机弹通知 → 点击 → 原生交给 Web → Web 打开会话
```

| 角色 | 职责 |
|---|---|
| Web | 发 `eventLogin` / `eventLogout`；把 `bundleId` 上报服务端 |
| 原生 | 集成 OneSignal SDK；按事件 `login` / `logout`；处理通知点击 |
| 服务端 | 按接收方 uid + 包名调 OneSignal REST API |
| OneSignal | 维护 `external_id` ↔ 设备映射，转发到 APNs / FCM |

`external_id` 就是 IM 的 uid 字符串，无前缀、无转换。

Web 不接触 OneSignal，也不使用 App ID。Web 只把 `bundleId` 上报给服务端，服务端按包名查到对应的 OneSignal App ID 和 REST API Key 后发推送。

**一个马甲包一个 OneSignal App，iOS 和 Android 都不共用别的包的 App ID。**

每个马甲包接入前：

1. 在 OneSignal 后台确认 App 已配置推送凭证：Android 绑定 FCM，iOS 上传 APNs 证书。没配的话 OneSignal 会直接拒发。
2. 把包名、平台、OneSignal App ID、REST API Key（`os_v2_app_` 开头）交给服务端配置。REST Key 必须属于这个 App，否则发送时返回 403。iOS 和 Android 包名不同（§13.2），两个平台各给一份。

## 5.2 绑定与解绑

```kotlin
// eventLogin
OneSignal.login(params.uid)

// eventLogout
OneSignal.logout()
```

`eventLogin` 对同一 uid 只发一次，但页面刷新后会重发，重复调 `login` 是安全的。`eventLogout` 必须调 `logout()`，否则换号后会收到前一个账号的推送。

## 5.3 通知点击

服务端下发的 `data`：

```json
{ "chat_id": "1571275627", "msg_id": "8842", "from_id": "1571275627" }
```

原生取 `chat_id` / `msg_id` 后调：

```js
window.__ssgShell.openChat({ chatId: '1571275627', messageId: 8842 })
```

- 等 `eventWebReady` 再调。冷启动点通知时 Web 还没初始化完，需把参数暂存，收到后再调。此时首屏已可见，用户会先短暂看到会话列表，再跳进会话。
- `chatId` 传字符串，`messageId` 传数字或可被 `Number()` 解析的字符串，可省略；省略时只打开会话，不定位到具体消息。
- payload 可以是对象或 JSON 字符串；字段名 `chatId`/`chat_id`、`messageId`/`msg_id`/`message_id` 都兼容。
- 只调一次。Web 内部会等会话数据就绪（最长 20 秒）再跳转，不需要原生重试。超过 20 秒还没拿到会话数据时，只打开会话，不定位消息；未登录时这次请求直接作废。
- Web 打开会话时新增一条历史记录，不替换当前页。冷启动点通知进入会话后，按返回会回到会话列表，原生不需要为此做「重新加载首页」之类的兜底。

## 5.4 体验细则

| 项 | 要求 | 依据 |
|---|---|---|
| 前台抑制 | App 在前台且用户正停留在该会话时，不弹系统通知；停在会话列表或其他会话时照常展示 | 原生记住最近一次 `chatOpen` 的 `chatId`，收到 `chatClose` 时清空；推送的 `chat_id` 等于它就不展示 |
| 角标 | 角标数 = Web 给的未读总数，`count` 为 `0` 时清零 | `unreadCount` |

- `chatId` 与推送里的 `chat_id`、`openChat` 的 `chatId` 是同一套取值：私聊为对方 uid，群和频道为负数 id，统一按字符串比较。
- 这几个事件只表示 Web 页面里的状态。App 是否在前台由原生自己判断：切到后台不会发 `chatClose`，回前台也不会重发 `chatOpen`。
- 本期不要求按会话清除通知：服务端不下发分组字段，原生无法可靠区分会话，不验收。`chatRead` 事件照常发送（进入本来就没有未读的会话时也会发一次），原生可以不处理。
- `unreadCount` 不含免打扰会话，只在数值变化时发。冷启动时 Web 先按本地缓存发一次（全新安装时是 `0`），同步完成后如有变化再发，所以角标可能先短暂显示旧值。退出登录时发 `0`。
- 页面重新加载（reload、重建 WebView、被踢下线后刷新）时不会发 `chatClose`。原生在页面开始加载时要清空记住的 `chatId`；加载完如果还停在会话里，Web 会重新发 `chatOpen`、`chatRead` 和 `unreadCount`。
- 后端只在用户离线时推送。App 在前台且连接正常时服务端本来就不推，前台抑制主要覆盖断线重连的那几秒。

# 6. 权限

## 6.1 用到的能力

| 功能 | Web 侧 API | 系统权限 | 不给的表现 |
|---|---|---|---|
| 发语音 | `getUserMedia({audio:true})` | 麦克风 | 点语音按钮后弹「麦克风权限被拒绝，请在系统设置中允许后重试」 |
| 发图片 / 视频 | `<input type="file" multiple accept="image/png,image/jpeg,image/gif,video/mp4,video/quicktime">`，群或私聊限制发送类型时 `accept` 会收窄。只能从相册选，不能发文件，见 §7.3 | 无（系统照片选择器） | 点附件按钮完全没反应 |
| 改头像 | `<input type="file" accept="image/png,image/jpeg">` | 同上 | 同上 |
| 收推送 | OneSignal | 通知 | 收不到推送 |
| 复制图片 | `navigator.clipboard.write` | 无，需安全上下文 + 用户手势 | 复制失败 |

Web 没有定位、通讯录、日历、蓝牙，也没有音视频通话，这些权限不要申请。

## 6.2 申请时机

用到的那一刻才申请，启动阶段一律不申请。

| 权限 | 时机 | 说明 |
|---|---|---|
| 麦克风 | 第一次点语音按钮 | 由 `getUserMedia` 触发，原生在授权回调里再向系统申请 |
| 相册 | 点附件按钮、拉起选择器 | 用系统照片选择器（Android Photo Picker、iOS `PHPickerViewController`），不申请相册权限 |
| 通知 | 收到 `eventLogin` 之后 | 未登录状态弹授权拒绝率极高，多数系统不允许二次申请 |
| 电池优化白名单 | 不在首启弹 | 放设置页引导，或用户反馈收不到消息时再引导 |

权限被永久拒绝后的二次引导由原生负责。Web 只能弹一句提示，拿不到系统设置页。

## 6.3 Android 声明

```xml
<uses-permission android:name="android.permission.INTERNET" />
<uses-permission android:name="android.permission.ACCESS_NETWORK_STATE" />
<uses-permission android:name="android.permission.RECORD_AUDIO" />
<uses-permission android:name="android.permission.MODIFY_AUDIO_SETTINGS" />
<uses-permission android:name="android.permission.POST_NOTIFICATIONS" />
<uses-permission android:name="android.permission.VIBRATE" />
```

`MODIFY_AUDIO_SETTINGS` 不需要运行时申请，但必须声明。WebView 录音同时依赖它和 `RECORD_AUDIO`，缺了它，用户授权麦克风后 Web 仍会提示无法录音。

不要声明 `READ_EXTERNAL_STORAGE` / `READ_MEDIA_IMAGES` / `READ_MEDIA_VIDEO`。用系统照片选择器就能拿到用户选中的文件，多声明会在市场审核时被追问用途。

## 6.4 iOS 声明

| `Info.plist` Key | 用途 | 必须 |
|---|---|---|
| `NSMicrophoneUsageDescription` | 发语音 | 是。缺失会在调 `getUserMedia` 时直接崩溃 |
| `NSPhotoLibraryUsageDescription` | 选图片 / 视频 | 是。`PHPicker` 本身不需要授权，按审核惯例保留用途说明 |

Capabilities：Push Notifications、Background Modes → Remote notifications。

用途文案写成用户看得懂的说明（如「用于录制并发送语音消息」），审核会逐条看。

# 7. WebView 回调

下面每一项不实现都表现为某个功能「点了没反应」，而 Web 侧看不到任何错误。

## 7.1 Android

| 回调 | 用途 | 不实现的后果 |
|---|---|---|
| `onShowFileChooser` | 发图片和视频 / 改头像 | 附件按钮完全没反应 |
| `onPermissionRequest` | 授予 `RESOURCE_AUDIO_CAPTURE` | 语音录不了 |
| `onPermissionRequestCanceled` | 清理授权 UI | 残留弹窗 |
| `onShowCustomView` / `onHideCustomView` | 视频全屏 | 点全屏没反应 |
| `onCreateWindow` | `target="_blank"` / `window.open` | 点链接没反应 |
| `onRenderProcessGone` | 渲染进程被回收或被主动结束后，销毁旧 WebView、新建一个加载入口地址，并返回 `true`（旧实例已不可用，不能对它 reload；返回 `false` 会连带杀掉 App） | 永久白屏，只能杀进程重进 |
| `onReceivedError` / `onReceivedHttpError` | 首屏加载失败 | 停在 WebView 默认错误页 |
| `shouldOverrideUrlLoading` | 外链、`tel:`、`mailto:` 交给系统 | 外链在 WebView 里打开，用户出不来 |
| `onConsoleMessage` | 转发到原生日志 | 线上问题无法定位，见 §11.6 |

`shouldOverrideUrlLoading` 必须原样放行同源 HTTPS，不做改写、重定向或拦截，只处理非 http(s) scheme 和跨域外链。`blob:` / `data:` 的导航不是外链，不要拦，那是 Web 预览媒体的通道。

## 7.2 iOS

| 回调 | 用途 | 不实现的后果 |
|---|---|---|
| `requestMediaCapturePermissionFor` | 授予麦克风（iOS 15+） | 语音录不了 |
| `createWebViewWith` | `window.open`：返回 nil 并在当前 WebView 加载 | 点链接没反应 |
| `webViewWebContentProcessDidTerminate` | 内容进程被回收后 `reload()` | 永久白屏 |
| `decidePolicyFor navigationAction` | 外链走 `UIApplication.open` | 外链在 WebView 里打开 |
| `didFailProvisionalNavigation` | 首屏加载失败重试 | 停在白屏 |

文件选择由系统接管，不需额外实现，但 `Info.plist` 的用途说明必须齐全（§6.4）。

## 7.3 文件选择器

点附件直接进入系统相册，中间不出现任何选择菜单（「文件」「拍照」「录制视频」等都不要）。进入相册后可以单选，也可以多选，图片和视频都能选，选完直接发送。不能发文件。两端都按这个要求实现。

Android：`onShowFileChooser` 直接拉起系统照片选择器，不要弹「相机 / 文件 / 文件管理器」之类的选项，也不要用 `fileChooserParams.createIntent()`，它会打开文档选择器。

1. 附件（`acceptTypes` 同时有 `image/*` 和 `video/*`）用 `PickMultipleVisualMedia(ImageAndVideo)`，图片和视频在同一个相册里选；改头像（只有图片）用 `PickVisualMedia(ImageOnly)`。
2. 支持单选和多选：`fileChooserParams.mode == MODE_OPEN_MULTIPLE` 时用多选版本，多选版本里只选一张也能直接确认，不要求至少选两张；不要限制成只能单选。
3. 用户取消时必须回调 `filePathCallback.onReceiveValue(null)`。漏了这一步，此后点附件按钮永久无反应。

iOS：WKWebView 自带的处理会先弹「照片图库 / 拍照或录像 / 选取文件」菜单，且没有公开接口去掉，所以要由壳接管附件选择，改用系统照片选择器 `PHPickerViewController`。只用公开 API，符合 App Store 审核要求，不要 hook WebKit 私有类（如 `WKFileUploadPanel`）。

1. **拦截**：用 document-start 的 `WKUserScript`（只注入主框架）拦截 `<input type="file">` 的弹出，包括 `click()`、`showPicker()` 和用户直接点击，读取它的 `accept` 和 `multiple`，经 `messageHandlers` 通知原生，不再走 WebKit 的默认菜单。
2. **弹出相册**：原生用 `PHPickerViewController`：
   - `multiple` 时 `selectionLimit = 0`（不限张数，选一张也能直接确认），否则为 `1`（改头像）
   - `filter` 按 `accept` 决定：同时有图片和视频时为 `.any(of: [.images, .videos])`；只有图片时为 `.images`；群或私聊限制发送类型时 `accept` 会收窄，照此收窄
   - `PHPicker` 不需要相册权限，不要先申请相册权限，也不要换成需要权限的 `PHPhotoLibrary` 自建相册
3. **格式**：Web 只收 png、jpeg、gif、mp4、mov，其他类型会被拒收。不接管时这一步由 WebKit 完成，接管后必须由壳完成：
   - 图片：GIF 保持原样，其他图片（HEIC、HEIF 等）一律转成 JPEG，交给页面的类型必须是 `image/jpeg`。用 `loadFileRepresentation(forTypeIdentifier: UTType.jpeg.identifier)` 取文件；取不到时用 ImageIO 解码后重新编码成 JPEG
   - 视频：取 `UTType.movie`，保留原始 mov 或 mp4
   - `loadFileRepresentation` 回调里的临时文件在回调结束后会被删除，要先复制出来
4. **交回页面**：把选中的文件变成页面里的 `File` 对象，通过 `DataTransfer` 赋给原来那个 `input.files`，再依次派发冒泡的 `input` 和 `change` 事件。Web 以这两个事件为准取文件，不需要改动。
   - 文件名：带上原文件名（`itemProvider.suggestedName` 加实际扩展名），不要用临时文件名；MIME 类型要和实际内容一致
   - 传输：视频可能有几百 MB，不要把整个文件转成 base64 一次性交给页面。用分块传输：原生按块读文件，每块 base64 后不超过 2 MB，由页面通过 `WKScriptMessageHandlerWithReply` 逐块拉取（或原生分次 `evaluateJavaScript` 推送），页面把每块解码成 `Uint8Array` 后用 `new Blob(parts)` 拼成文件。不要用 `WKURLSchemeHandler` 自定义 scheme：HTTPS 页面向自定义 scheme 发的 `fetch` 和 XHR 都会被 WebKit 拦截
   - 大小：不要静默丢弃用户选中的文件。确实需要设上限时，超限要给用户明确提示
5. **取消**：用户取消时不派发事件，下一次点附件要能再次拉起
6. **不能落回默认菜单**：拦截必须覆盖所有文件输入框，任何情况下都不能再出现 WebKit 的「照片图库 / 拍照或录像 / 选取文件」菜单

Web 侧兜底：不管从哪个入口选，只接收 png、jpeg、gif、mp4、mov，其他文件会被跳过并提示「仅支持发送图片和视频」。

## 8.1 硬性要求

| 项 | 要求 | 不满足的后果 |
|---|---|---|
| 协议 | HTTPS，`isSecureContext === true` | Service Worker 无法注册，媒体加载与缓存全部降级 |

## 8.3 存储不要清

以下调用不允许出现在任何常规路径上，只能由用户显式「清除数据」触发：

- Android：`clearCache()`、`clearWebStorage()`、`WebStorage.getInstance().deleteAllData()`、`CookieManager.removeAllCookies()`、`deleteDatabase`
- iOS：`WKWebsiteDataStore.removeData(ofTypes:)`、使用 `nonPersistent()`
- iOS 用 Flutter 插件承载时：插件的 `clearCache()` / `clearLocalStorage()`
- 两端：往页面注入 JS 清空 `caches`（CacheStorage）或注销 Service Worker

资源加载失败时的兜底只做 reload，不要顺手清缓存。SDK 里「启动时清缓存」一类的配置项，默认值必须是关闭。

清存储的后果：用户被登出、本地消息缓存全失、媒体重新下载一遍、诊断上下文丢失，并且 `eventRegister` 的「每设备一次」标记被抹掉，渠道注册数虚高。「启动时清一次缓存保证干净」是禁止的做法。

## 8.4 承载方式（Android）

IM 的 WebView 必须由原生 View 承载，不能作为 Flutter 的 PlatformView 嵌入。`flutter_inappwebview` 的 `InAppWebView`、`webview_flutter` 的 `WebViewWidget`、自己用 `AndroidView` / `PlatformViewLink` 包的 WebView 都不行，混合合成（Hybrid Composition）和纹理合成（Texture Layer）都不行。

PlatformView 下 WebView 的每一帧都要和 Flutter 画面合成后才能上屏，登录页、键盘弹起收起、Tab 切换会明显掉帧；原生承载时同一页面每帧在 18ms 以内。

App 其余部分可以继续用 Flutter：

- 进入 IM 时打开一个原生 Activity，WebView 作为它的内容视图。
- WebView 由 Application 级单例创建和持有，Activity 只负责挂上和取下，满足 §10.5 单实例和 §10.6 长活。
- 本规范对 WebView 的要求全部在原生实现：`addDocumentStartJavaScript`（§1.2）、`jsBridge`（§3.3）、`WebChromeClient` / `WebViewClient` 回调（§7.1）、`adjustResize`（§9.2）、insets（§9.4）。
- 原生与 Flutter 之间用 MethodChannel 通信：进入 IM、推送点击打开会话（§5.3）、把 Web 事件转给 Dart 处理。

```kotlin
object ImWebViewHolder {
    private var webView: WebView? = null

    fun current(): WebView? = webView

    fun get(ctx: Context): WebView = webView ?: WebView(MutableContextWrapper(ctx.applicationContext)).also {
        // §8.2 设置、§2.2 UA、§1.2 注入、§3.3 jsBridge、§7.1 回调
        it.loadUrl(ENTRY_URL)
        webView = it
    }
}

class ImActivity : ComponentActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        val container = FrameLayout(this)
        container.setOnApplyWindowInsetsListener { v, insets ->
            val i = insets.getInsets(WindowInsets.Type.systemBars() or WindowInsets.Type.ime() or WindowInsets.Type.displayCutout())
            v.setPadding(i.left, i.top, i.right, i.bottom)
            WindowInsets.CONSUMED
        }
        setContentView(container)
        val web = ImWebViewHolder.get(this)
        (web.parent as? ViewGroup)?.removeView(web)
        container.addView(web, FrameLayout.LayoutParams(-1, -1))
    }

    override fun onDestroy() {
        ImWebViewHolder.current()?.let { (it.parent as? ViewGroup)?.removeView(it) }
        super.onDestroy()
    }
}
```

```dart
const shell = MethodChannel('shell');
shell.invokeMethod('openIm');   // 原生侧 startActivity(Intent(this, ImActivity::class.java))
```

`ImActivity` 在 Manifest 里声明 `android:windowSoftInputMode="adjustResize"`、`android:launchMode="singleTask"`，`configChanges` 按 §10.6。返回键按 §9.1。

### 体验与性能

1. **提前创建 WebView**：B 面开启时，在 `Application.onCreate` 里就调 `ImWebViewHolder.get(this)` 创建 WebView 并开始加载入口地址，不要等进入 IM 页面再建。WebView 内核首次初始化要几百毫秒，提前做能直接缩短冷启动。B 面未开启时不要预加载 IM。
2. **启动画面用系统 SplashScreen**：B 面开启时，冷启动的第一个 Activity 就是 `ImActivity`，在 `onCreate` 里先调 `installSplashScreen()`，再用 `setKeepOnScreenCondition { !webReady && 未超过 30 秒 }` 让系统启动图一直撑到收到 `eventWebReady`（§9.6）。这样不需要另做一层 splash，也不会先画出 Flutter 页面。B 面未开启时由 `ImActivity` 转去 Flutter 的 A 面并结束自己。
3. **背景色与首屏一致**：`ImActivity` 主题里的 `android:windowBackground` 和 `webView.setBackgroundColor()` 都设成页面首屏的颜色（白色 `#FFFFFF`）。启动、键盘弹收、Activity 切换时边缘不会闪出黑色或别的颜色。
4. **release 包保留桥接方法**：`jsBridge.postMessage` 只被 JS 调用，R8 / ProGuard 没有对应的 keep 规则时会把它混淆或删掉，release 包里所有 Web 事件丢失，debug 包测不出来。AGP 的默认规则文件（`getDefaultProguardFile("proguard-android-optimize.txt")`）已经带了下面这条；没有引用默认文件、或换了自己的规则文件时，必须自己加上：

   ```
   -keepclassmembers class * {
       @android.webkit.JavascriptInterface <methods>;
   }
   ```

   提测前用 release 包确认原生能收到 §3.1 的事件。
5. **渲染进程优先级**：创建 WebView 后调 `webView.setRendererPriorityPolicy(WebView.RENDERER_PRIORITY_IMPORTANT, true)`（Android 8.0+）。前台时降低渲染进程被系统回收的概率，第二个参数为 `true` 表示不可见时自动降级，不影响后台省电。
6. **保持硬件加速**：不要关闭 `android:hardwareAccelerated`，不要对 WebView 或它的父容器调 `setLayerType(LAYER_TYPE_SOFTWARE, …)`，也不要为了圆角、截图、阴影给 WebView 套裁剪或离屏绘制。软件绘制下滚动和键盘动画会明显卡顿。
7. **适配预测性返回**：返回键用 `OnBackPressedDispatcher` 注册回调（`ImActivity` 继承 `ComponentActivity`），并在 Manifest 的 `<application>` 上声明 `android:enableOnBackInvokedCallback="true"`，Android 14 以上的返回手势才有预览动画并走同一套逻辑（§9.1）。

### 自测

- 登录页反复点输入框弹出、收起键盘，`adb shell dumpsys gfxinfo <包名> framestats` 统计每帧耗时，99 分位不超过 25ms，超过 33ms 的帧不超过 1%。
- 用 release 包冷启动：只看到系统启动图，然后直接是页面；原生日志能收到 `eventWebReady`、`eventLogin` 等事件。

# 9. 交互

## 9.1 Android 返回键

Web 用 `history.pushState` 管理会话、弹层、面板的层级，返回键必须先回退 Web 的历史。直接 `finish()` 会导致用户在会话里按返回键就退出整个 App。

```kotlin
onBackPressedDispatcher.addCallback(this) {
    if (webView.canGoBack()) webView.goBack()
    else moveTaskToBack(true)   // 栈底退到后台，不销毁 WebView（§10.6）
}
```

手势返回走同样逻辑，Manifest 声明见 §8.4 体验与性能第 7 条。不要调 `webView.clearHistory()`。

## 9.2 键盘

- Activity 必须 `android:windowSoftInputMode="adjustResize"`，Web 靠窗口尺寸变化调整布局。
- 用了沉浸式 / edge-to-edge 时，`adjustResize` 在 Android 11+ 会失效，必须自己消费 `WindowInsets.ime` 并把高度变化反映到 WebView 的布局高度。
- iOS 由 Web 处理：键盘弹出时 WebView 的 frame 保持不变，不要跟着键盘缩小，也不要做 frame 偏移或 `contentInset` 调整。Web 用「WebView 高度 − `visualViewport` 高度」算出键盘高度，自己把会话区收到键盘上方，并把系统自动滚走的页面拉回顶部。原生再改一次就会叠加成两倍位移。

## 9.3 字体与缩放

```kotlin
webView.settings.apply {
    textZoom = 100          // 跟随系统字体放大会让布局错位
    setSupportZoom(false)
    builtInZoomControls = false
    displayZoomControls = false
}
```

页面已声明 `user-scalable=no`，iOS 侧不需额外处理。

## 9.4 安全区域

**WebView 只放在安全区内**：由原生把 WebView 摆在状态栏 / 刘海 / 灵动岛以下、Home 指示条（Android 为导航栏）以上。Web 在壳内只按 `env(safe-area-inset-*)` 留白，不再用机型兜底值，所以 `env()` 必须为 0。

- iOS：WebView 约束到 `safeAreaLayoutGuide`（Flutter 用 `SafeArea` 包住 WebView，top 与 bottom 都开）。`scrollView.contentInsetAdjustmentBehavior = .never` 保留。
- Android：不开 edge-to-edge，WebView 位于状态栏与导航栏之间；已开 edge-to-edge 的，给 WebView 容器加 `WindowInsets.systemBars` 的 padding。
- 安全区外露出的状态栏 / 底部条一律用白色（`#FFFFFF`）背景、状态栏深色图标。登录页、深色模式下也一样，不要按页面颜色取色或切换。
- 不要再额外给 WebView 加 padding 或 `contentInset`。WebView 放进安全区后页面内 `env(safe-area-inset-*)` 必须为 0，Web 侧才不会重复留白。
- Android 在承载 WebView 的容器上把 `systemBars`、`ime`、`displayCutout` 的 insets 转成 padding 并返回 `CONSUMED`（写法见 §8.4），不要让 insets 再传进 WebView，否则页面读到的 `env()` 不为 0，顶部和底部各多一段空白。自测时在页面里读 `env(safe-area-inset-top)`，应为 0。

自测：会话列表顶部的「编辑」「+」、会话页的返回键和头像都在状态栏下方且可点击；图片查看器右上角关闭键可点击；输入栏不压 Home 指示条。

## 9.5 长按与滚动

- Web 自己实现了消息长按菜单，并用 `user-select` 控制可选区域。原生不要附加长按手势识别器或自定义 ActionMode。
- iOS：`webView.scrollView.bounces = false`，避免整页橡皮筋把聊天界面拉出来。
- 不要给 WebView 外层套可滚动容器。

## 9.6 启动与错误态

### 启动不出现多余加载

已开启 B 面时，冷启动直接加载 Web，从点开图标到页面可用，用户只能看到两样东西：

1. 系统启动图（iOS LaunchScreen、Android SplashScreen）
2. 一屏原生 splash，用来遮住 WebView 加载期间的白屏，画面与系统启动图一致（同一张图或同一底色加 logo），两者衔接起来看就是同一个启动画面

除此之外不允许出现任何加载界面。以下都算违规：
- 自定义 loading 页、白底或纯色页加进度条、转圈、骨架屏
- 「正在连接」「正在初始化」之类的提示页
- 开屏广告、欢迎页、引导页
- A 面的启动页、加载动画、资源下载进度

WebView 在启动后立即开始加载入口地址，不要等其他初始化做完再加载。B 面开关的判断不能以等待界面的形式出现在用户面前，比如把上次的结果缓存在本地，冷启动直接按缓存走。

未开启 B 面、展示的是 A 面时，A 面自己的加载界面不受本节限制。一旦开启 B 面，A 面相关的加载画面一律不再出现，包括从 A 面切到 B 面的过程。

### splash 撤除与错误态

- 收到 `eventWebReady` 后立即撤 splash，此时首屏已经画好，不要用固定时长定时器。
- `eventWebReady` 可能永远不来：内核过低时 Web 只显示不兼容提示页，脚本加载失败或初始化失败时 Web 显示重试页，都不会发。splash 要有上限（建议 30 秒），到时撤掉 splash，让用户看到页面或原生重试页。
- 首屏加载失败（无网、DNS 失败）接管为原生重试页，不要露出 WebView 默认错误页。
- SSL 错误不要无脑 `proceed()`，也不要静默 `cancel()` 停在白屏，要给用户可见提示。
- 不要在壳内再做一层下载 / 升级引导 UI，Web 已内置且在壳内会自动隐藏。
- 注入调试工具时不要覆盖 `window` 上的现有字段，覆盖了 `__ssgShell` 会让回调全丢。

# 10. 保活与假死防护

假死 = 界面正常、能点能滑，但消息不进不出，要杀进程重进才恢复。

## 10.1 机制

Web 侧有三层看门狗：

| 层 | 机制 | 周期 | 位置 |
|---|---|---|---|
| 1 | MTProto `PingDelayDisconnect`，超时重连 sender | 10 秒，超时 8 秒 × 3 次 | Web Worker |
| 2 | `updates.GetState` 探活，超时 8 秒，连续 2 次失败触发强制重连 | 40 秒（移动端） | Web Worker |
| 3 | 主线程 ping Worker，超时 4 秒，2 次无响应就杀掉重建 | 事件驱动，主线程没有定时器，靠下面的信号和 `onHeartbeat` 触发 | 主线程 |

前两层都跑在 Web Worker 的定时器上，第三层完全靠事件触发。所以假死只有一种根因：Worker 的定时器被冻住或 Worker 被系统回收，同时主线程又没收到任何事件去发起检查。此时三层一起失效，主线程发给 Worker 的重连指令进了黑洞——`postMessage` 不报错、不超时、没有确认。

本节和 §11 的每条要求都是为了避免这个状态，或在它发生后能被捅醒。

## 10.2 回前台信号

回前台时，Web 要做两件事：ping Worker（第三层），以及让 Worker 强制重连。各信号的作用不一样，马甲包至少要保证前两个能到：

| 信号 | 来源 | ping Worker | 强制重连 | 马甲包里能不能到 |
|---|---|---|---|---|
| `__ssgShell.onForeground()` | 原生主动调 | 是 | 是 | 实现了就能到，最可靠 |
| `visibilitychange` | 调了 `webView.onPause()` / `onResume()` 才翻转 | 是 | 是 | 不调就永远不触发 |
| `freeze` / `resume` | 同上，Page Lifecycle 事件 | 否 | 是 | 同上。Worker 已死时重连指令发不到，单靠它救不回来 |
| `window.focus` | WebView 在 App 切换时通常不触发 | 是 | 否 | 基本到不了 |

两件事都要做，不要二选一：

1. 每次回前台都调 `onForeground()`。锁屏解锁、从后台任务切回、从通知点进来都算。
2. 实现 `webView.onPause()` / `onResume()`（Android）。`document.hidden` 翻转后 `visibilitychange` 就是第二条独立通道。

注入生效后，后台停留超过 1.5 秒回前台即立刻重连。没有注入时走浏览器口径：后台必须超过 8 秒才重连，还要再等 500ms 去抖，2～7 秒的短暂切后台回来根本不重连。

## 10.3 不要冻结定时器

- 不要调 `pauseTimers()`。它冻结整个 WebView 的 JS 定时器，包括 Worker 里的心跳和探测，而主线程没有定时器兜底。
- `onPause()` 可以调（只暂停渲染和可见性），`pauseTimers()` 不可以。这两个 API 经常被一起写，必须分开。
- 不要用「后台降频」「省电策略」限制 WebView 的 JS 执行。
- Android 申请电池优化白名单，避免进程被 Doze 冻死；必要时用前台服务。

## 10.4 网络恢复单独通知

回前台瞬间网络往往还没真正可用（Wi-Fi 重连、蜂窝重新附着要几秒），此时 Web 发起的重连会失败。`onForeground` 和 `onNetwork` 不受重连冷却限制，每次都会让 Web 立刻检查连接并拉取最新消息；连接还在重试等待时会马上再试一次。

1. `onForeground()` 照常在回前台第一时间调。
2. 网络真正可用之后再调一次 `onNetwork(type)`。判据是「能发出请求」，不是 `ConnectivityManager` 的第一跳回调，那时常常还没拿到 IP。
3. Wi-Fi ↔ 蜂窝切换也要调，去抖 1～2 秒，不要每个系统回调都转发。
4. 断网时不用调，`onNetwork('none')` 会被 Web 忽略。不要在网络还没通时提前调：那次重试会失败，之后要等下一次重试。

## 10.5 只开一个 WebView 实例

Web 用 BroadcastChannel 在同源页面之间选举主实例，只有主实例建立长连接，其他实例从主实例同步界面状态。

如果 App 里同时存在第二个加载同一域名的 WebView，可见的那个可能被选为从实例，它不建连接，界面靠同步数据渲染，看着完全正常。持有主实例身份的 WebView 被冻住时也不会让出身份。

- IM 页面只开一个 WebView 实例。
- 其他 H5（活动、客服、落地页）换一个域名，或用系统浏览器打开。
- 不要为了预加载提前创建隐藏的同域 WebView。

## 10.6 实例长活

- 不要在切后台、锁屏、切 Tab 时销毁 Activity / WKWebView，也不要「每次进入重建 WebView」。重建 = 重新加载整个 Web = 重建长连接 + 重拉历史。
- Android 用 `android:configChanges` 覆盖旋转等变化，避免 Activity 重建。

## 10.7 做不到的

iOS 后台保持长连接是系统限制，Android 被系统或厂商强杀后自启不在本次范围内，这两种都靠推送补齐。恢复速度完全取决于 §10.2 的信号有没有到。

# 11. 新增契约

本节 Web 侧实现已完成。字段与时机以本节为准。

## 11.1 原生心跳

```js
window.__ssgShell.onHeartbeat()
```

- 前台每 20 秒调一次，进后台停止，回前台恢复。
- 必须用原生定时器（Android `Handler` / iOS `Timer`）。用 WebView 里的 JS 定时器会被一起冻住，等于没做。
- Web 收到后 ping 自己的 Worker，没响应就就地重建，用户无感。

## 11.2 存活监测与兜底 reload

Web 侧前台每 15 秒发一次 `eventWebAlive`（§3.1）。原生侧：

0. 收到第一条 `eventWebAlive` 之后才开始计时，在那之前永远不判定卡死。否则原生先上线、Web 还没发，会每 60 秒 reload 一次。
1. 记录最后一次收到的时间。
2. App 在前台、且超过 60 秒没收到 → 判定卡死，`webView.reload()`。
3. reload 后 10 秒内页面没有开始加载（Android `onPageStarted`，iOS `didStartProvisionalNavigation`；页面主线程卡死时，WebKit 会把 reload 排在卡住的 JS 后面，reload 不生效）→ 销毁并重建 WebView（Android 在 `ImWebViewHolder` 里重新创建实例；iOS 用 Flutter 插件时给 `InAppWebView` 换 `Key`），重新加载入口地址。
   - **Android 必须先结束渲染进程再重建。** 同一个 App 的所有 WebView 共用一个渲染进程，死循环卡住的是这个进程，只换 WebView 实例的话，新实例同样卡住，永远加载不出来。做法：`WebViewCompat.getWebViewRenderProcess(webView)?.terminate()`（androidx.webkit，先用 `WebViewFeature.isFeatureSupported(WEB_VIEW_RENDERER_TERMINATE)` 判断），随后在 `onRenderProcessGone` 里重建（§7.1）。不支持 `terminate()` 的旧内核只能重启 Activity 进程兜底。
   - iOS 每个 WKWebView 的 WebContent 进程随实例销毁，直接重建即可。
4. 后台期间不计时、不判定。回前台时把「最后收到时间」重置为当前时间：Web 在 `onBackground` 后停发，回前台后要等下一个 15 秒周期才发，不重置会被误判卡死。
5. 同一次卡死只处理一次，页面恢复后才允许下一次。连续失败要退避：第一次处理后等 180 秒，之后 600 秒，不能进 reload 循环。
6. reload / 重建前后各记一条本地日志。

这是唯一能从主线程彻底卡死里恢复的机制，那种状态下只有原生看得见。

## 11.3 推送捅醒

一条消息的推送到达而 App 正在前台，说明这条消息 Web 没有通过长连接收到，连接已死。

原生在推送回调里判断 App 是否在前台。如果在前台，除了按 §5.4 抑制通知，额外调一次：

```js
window.__ssgShell.onNetwork('<当前网络类型>')
```

## 11.4 内存告警

```js
window.__ssgShell.onMemoryWarning()
```

- Android：`onTrimMemory` 的 `level` 为 `TRIM_MEMORY_RUNNING_LOW` 或 `TRIM_MEMORY_RUNNING_CRITICAL` 时调。不要写成 `level >= TRIM_MEMORY_RUNNING_LOW`：切后台时系统必发 `TRIM_MEMORY_UI_HIDDEN`（值 20，比 `RUNNING_LOW` 的 10 大），会被误当成内存告警。
- iOS：只在 `didReceiveMemoryWarning`（`UIApplicationDidReceiveMemoryWarningNotification`）时调。
- 切后台、回前台都不应触发。
- Android 在 Application 的 `onTrimMemory` 里判断后直接调用，不要经 Flutter 的 `didHaveMemoryPressure` 转发；iOS 用 Flutter 时同样直接监听系统通知。

Web 收到后裁剪媒体内存缓存并上报一条诊断，降低渲染进程被系统回收的概率。

## 11.5 诊断字段

`__SSG_SHELL__` 的 `deviceModel` 和 `osVersion`（§1.1）。假死集中在特定厂商的省电策略上，小米、华为、OPPO 的 Doze 实现差异很大，有这两个字段才能按机型定位。

## 11.6 日志导出

- `onConsoleMessage`（Android）和 iOS 侧的 console 转发，把 Web 的 console 落到原生日志。
- 提供隐藏入口（如设置页连点若干次），能查看并导出：当前 URL、UA、WebView 内核版本、`__SSG_SHELL__` 内容、最近一次 reload 时间、最近 N 条 console。

## 11.7 内核版本引导

Android 的 WebView 是可独立更新的系统组件，老设备上可能停留在很旧的版本。

启动时读 `WebViewCompat.getCurrentWebViewPackage()?.versionName`，低于 92（§8.1）时一次性提示用户更新「Android System WebView」或 Chrome，允许忽略，不要阻断启动。

# 13. 包信息

## 13.1 应用名称

应用名称指桌面图标下显示的名称：iOS 的 `CFBundleDisplayName`（没有时取 `CFBundleName`），Android 的 `android:label`。

- 只能由英文字母和中文汉字组成，英文大小写都可以；不能有数字、符号、空格
- 英文部分不能出现 `i o l j g z y u` 这 8 个字母，大小写都不行（`I O L J G Z Y U`）。这些字母和别的字母、数字形近，或者读音容易混淆
- 也就是说，英文字母只能从下面 18 个里选，大小写不限：`a b c d e f h k m n p q r s t v w x`
- 各语言的本地化名称（iOS `InfoPlist.strings`，Android `values-*/strings.xml`）同样要符合以上规则

示例：`Fresca`、`PentaMax`、`浮光灯港`、`灯港Vera` 符合；`Lumen Quay`（有空格，有 `l`、`u`、`y`）、`Chat2Go`（有数字和 `g`）、`灯港·Bay`（有符号和 `y`）不符合。

## 13.2 包名

包名指 iOS 的 Bundle ID（`PRODUCT_BUNDLE_IDENTIFIER`）和 Android 的 `applicationId`。

**iOS 和 Android 的包名不能相同。** 服务端按包名保存推送配置，一个包名只能配置一个平台。两端包名相同时，另一端配不进去，收不到推送。

示例：iOS 用 `com.example.app`，Android 用 `com.example.app.android`。
